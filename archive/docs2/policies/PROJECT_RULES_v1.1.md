# PROJECT_RULES_v1.1 - полный свод правил проекта

Файл: `docs2/policies/PROJECT_RULES_v1.1.md`

Этот документ дополняет `PROJECT_RULES_v1.0.md`.
Новые обязательные акценты текущей версии:
- `core` - единственный рабочий контур;
- `legacy` - только архивный reference, без отдельного roadmap;
- режим критика - обязательный стиль по умолчанию;
- документация не плодит новые версии без реального изменения source of truth;
- предыдущие версии основных документов хранятся в `docs2/history/`.

## 1. Производственные правила из старого docs

### 1.1. Патчи только архивом и только измененные файлы
- Каждый кодовый патч передается архивом.
- В архив кладутся только измененные файлы, а не весь проект.
- Полный проект отправляется только если это отдельно согласовано.

### 1.2. Если есть сомнения в версии файла - правки стоп
- Если файл отсутствует в архиве, не виден или есть сомнение в его актуальности:
  - правки не вносятся;
  - сначала запрашивается актуальный файл или новый архив.

### 1.3. Все выводы и логи - только через корневую `out/`
- Любые результаты (`equity`, отчеты, свипы, диагностика, forward-test и т.д.) пишутся только в корневую `out/`.
- Внутри `app2/` и `app3/` не создаются собственные `out/`, `data/` и альтернативные каталоги результатов.

### 1.4. Self-check перед отправкой патча
Минимум перед отправкой:
- синтаксическая проверка (`ast.parse`, `python -m compileall`, `py_compile` или эквивалент);
- по возможности - короткий dry-run / smoke test / sanity check.

Сырые файлы без проверки не отправляются.

### 1.5. Не вставлять полный код файлов в чат без запроса
- В обычном режиме в чат не вставляется полный код файлов или большие куски.
- Сначала дается краткое описание изменений и архив.
- Полный код - только по прямому запросу пользователя.

### 1.6. Спорные архитектурные упрощения - только после обсуждения
- Нельзя молча "упростить под капотом" архитектуру, убрать слой, изменить фундаментальную логику или обойти договоренности.
- Любое спорное архитектурное упрощение сначала обсуждается.

## 2. Технические и структурные правила

### 2.1. Структура директорий
В корне репозитория:
- `data/` - сырые данные
- `processed/` - агрегированные бары и подготовленные временные ряды
- `out/` - результаты, отчеты, свипы, forward-тесты
- `docs/` / `docs2/` - документация
- `app2/` - основной рабочий контур
- `app3/` - будущий / online-контур

### 2.2. Стандарт вызова CLI
Команды запускаются в стиле:

```bash
python -m app2.cli <command> [аргументы]
```

Примеры в документации должны быть реально запускаемыми.

### 2.3. Режимы - основа логики
- Сначала определяется режим рынка (`trend`, `range`, `high_vol` и т.п.).
- Потом выбирается стратегия, профиль риска и параметры.
- Любые новые фичи / стратегии должны вписываться в эту декомпозицию, а не обходить ее.

### 2.4. Свип - это диагностика, а не магический оптимизатор
- Свип используется для диагностики устойчивости и профилей.
- Свип не заменяет нормальную логику стратегии и риск-менеджмента.
- Свип не используется как "подгонка до красоты".

### 2.5. `core` - единственный рабочий контур
- Активное развитие ведется только в `core`.
- `legacy` не является объектом отдельного roadmap.
- `legacy` не используется как обязательная база сравнения для принятия решений.
- Если нужен reference, он используется только как архивная справка, а не как ось планирования.

## 3. Правила по документации и миграции

### 3.1. Новая версия документа нужна не всегда
- Новая версия файла нужна только если реально меняется source of truth или стадия проекта.
- Небольшие уточнения и добавления в несколько строк могут вноситься в текущий файл без повышения версии.

### 3.2. Старое содержание дополняется, а не переписывается с нуля
- Текущее содержание документа не обнуляется без прямого согласования.
- Новая версия документа должна сохранять смысл и хронологию предыдущих версий.

### 3.3. Предыдущие версии должны храниться в `docs2/history/`
- В корне `docs2/` лежат только актуальные версии основных документов.
- Предыдущие версии хранятся в `docs2/history/` по семействам файлов.
- Базовые каталоги истории:
  - `history/readme/`
  - `history/doc_index/`
  - `history/contract/`
  - `history/model_plan/`
  - `history/operations/`
  - `history/policies/`

### 3.4. При миграции чата новый чат обязан сначала читать правила и договоренности
- Новый чат не должен сразу предлагать патчи или roadmap.
- Сначала он обязан:
  1. прочитать `docs2` source of truth,
  2. принять правила и договоренности,
  3. восстановить актуальную стадию проекта,
  4. и только после этого предлагать изменения.

## 4. Режим критика и режим агента

### 4.1. Режим критика обязателен
- Без лести.
- Без автосогласия.
- Если есть ошибка - она исправляется, а не сглаживается.
- Всегда оцениваются риски, слабые места и альтернативы.
- При нехватке данных прямо фиксируется, чего именно не хватает.
- Стиль ответа - жестко, коротко, по существу.

### 4.2. Режим агента работает короткими итерациями
- Агент работает шагами по 1-2 действия.
- Сначала опирается на фактическое состояние `app2`, а не на старые промежуточные описания.
- Не обещает широкую работу "позже" и не растягивает ответ обещаниями.
- Каждый шаг должен иметь:
  - цель,
  - список файлов,
  - ожидаемый результат,
  - self-check,
  - stop-condition при нехватке актуальных файлов или данных.

## 5. Правила работы с LLM и внешними аналитиками

### 5.1. ChatGPT
- Работает по patch-discipline и правилам из этого документа.
- Не меняет контракт или документацию молча.
- Должен сначала читать актуальные документы при миграции.
- Работает в режиме критика по умолчанию.

### 5.2. Qwen / локальная модель
- Используется как внешний reviewer, локальный debugger и источник гипотез.
- Не считается source of truth.
- Его предложения попадают в проект только после обсуждения и фиксации в docs / patch flow.

### 5.3. agent_hands
- На текущем этапе должен считаться read-only bridge к локальной модели.
- Не должен вносить скрытые изменения в проект.
- Не должен обходить patch / review / docs discipline.

## 6. Что считается нарушением правил

- правка неактуального файла без запроса актуальной версии;
- запись результатов не в корневую `out/`;
- отправка непроверенного патча;
- скрытая архитектурная "оптимизация";
- потеря хронологии документации;
- выпуск новой версии документов без реального изменения source of truth;
- хранение старых версий основных документов вперемешку в корне `docs2/`;
- миграция нового чата без чтения source-of-truth документов и правил;
- уход в режим лести, автосогласия или замалчивания рисков;
- возврат к roadmap, где `legacy` снова становится обязательным объектом сравнения.
