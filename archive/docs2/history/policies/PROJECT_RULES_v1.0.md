# PROJECT_RULES_v1.0 - полный свод правил проекта

Файл: `docs2/policies/PROJECT_RULES_v1.0.md`

Этот документ собирает **полный набор правил**, который ранее был размазан по старым `docs/READMEv*` и договорённостям в чатах.
Он не заменяет контракт и не заменяет план, а фиксирует именно **правила работы**.

## 1. Производственные правила из старого docs

### 1.1. Патчи только архивом и только изменённые файлы
- Каждый кодовый патч передаётся архивом.
- В архив кладутся только изменённые файлы, а не весь проект.
- Полный проект отправляется только если это отдельно согласовано.

### 1.2. Если есть сомнения в версии файла - правки стоп
- Если файл отсутствует в архиве, не виден или есть сомнение в его актуальности:
  - правки не вносятся;
  - сначала запрашивается актуальный файл или новый архив.

### 1.3. Все выводы и логи - только через корневую `out/`
- Любые результаты (`equity`, отчёты, свипы, диагностика, forward-test и т.д.) пишутся только в корневую `out/`.
- Внутри `app2/` и `app3/` не создаются собственные `out/`, `data/` и альтернативные каталоги результатов.

### 1.4. Self-check перед отправкой патча
Минимум перед отправкой:
- синтаксическая проверка (`ast.parse`, `python -m compileall`, `py_compile` или эквивалент);
- по возможности - короткий dry-run / smoke test / sanity check.

Сырые файлы без проверки не отправляются.

### 1.5. Не вставлять полный код файлов в чат без запроса
- В обычном режиме в чат не вставляется полный код файлов или большие куски.
- Сначала даётся краткое описание изменений и архив.
- Полный код - только по прямому запросу пользователя.

### 1.6. Спорные архитектурные упрощения - только после обсуждения
- Нельзя молча "упростить под капотом" архитектуру, убрать слой, изменить фундаментальную логику или обойти договорённости.
- Любое спорное архитектурное упрощение сначала обсуждается.

## 2. Технические и структурные правила

### 2.1. Структура директорий
В корне репозитория:
- `data/` - сырые данные
- `processed/` - агрегированные бары и подготовленные временные ряды
- `out/` - результаты, отчёты, свипы, forward-тесты
- `docs/` / `docs2/` - документация
- `app2/` - основной рабочий контур
- `app3/` - будущий / online-контур

### 2.2. Стандарт вызова CLI
Команды запускаются в стиле:

```bash
python -m app2.cli <command> [аргументы]
```

Примеры в документации должны быть реально запускаемыми.

### 2.3. Режимы - основа логики
- Сначала определяется режим рынка (`trend`, `range`, `high_vol` и т.п.).
- Потом выбирается стратегия, профиль риска и параметры.
- Любые новые фичи / стратегии должны вписываться в эту декомпозицию, а не обходить её.

### 2.4. Свип - это диагностика, а не магический оптимизатор
- Свип используется для диагностики устойчивости и профилей.
- Свип не заменяет нормальную логику стратегии и риск-менеджмента.
- Свип не используется как "подгонка до красоты".

## 3. Новые правила по документации и миграции

### 3.1. Изменение документа = новая версия файла
- Если документ меняется, имя версии файла должно меняться.
- Перезаписывать старую версию файла без изменения версии нельзя.

### 3.2. Старое содержание дополняется, а не переписывается с нуля
- Новая версия документа должна сохранять смысл и хронологию предыдущих версий.
- Исключения допускаются только после прямого согласования с пользователем.

### 3.3. При миграции чата новый чат обязан сначала читать правила и договорённости
- Новый чат не должен сразу предлагать патчи или roadmap.
- Сначала он обязан:
  1. прочитать `docs2` source of truth,
  2. принять правила и договорённости,
  3. восстановить актуальную стадию проекта,
  4. и только после этого предлагать изменения.

## 4. Правила работы с LLM и внешними аналитиками

### 4.1. ChatGPT
- Работает по патч-дисциплине и правилам из этого документа.
- Не меняет контракт или документацию молча.
- Должен сначала читать актуальные документы при миграции.

### 4.2. Qwen / локальная модель
- Используется как внешний reviewer, локальный debugger и источник гипотез.
- Не считается source of truth.
- Его предложения попадают в проект только после обсуждения и фиксации в docs/patch flow.

### 4.3. agent_hands
- На текущем этапе должен считаться read-only bridge к локальной модели.
- Не должен вносить скрытые изменения в проект.
- Не должен обходить patch / review / docs discipline.

## 5. Что считается нарушением правил

- правка неактуального файла без запроса актуальной версии;
- запись результатов не в корневую `out/`;
- отправка непроверенного патча;
- скрытая архитектурная "оптимизация";
- потеря хронологии документации;
- миграция нового чата без чтения source-of-truth документов и правил.
