## 1. Что зафиксировано по проекту

- roadmap строится только вокруг `core`;
- `legacy` не тянет на себя время и не участвует в активном planning loop;
- сначала опора на фактическое состояние `app2`, потом на старые промежуточные описания;
- Dataset A truth policy:
  - `Dataset A_research = candidates`
  - `Dataset A_policy = trades`.

## 2. Правило по документации

Документация не обновляется после каждого сообщения.

Новая версия файла нужна только если реально меняется source of truth или стадия проекта.
Если меняются или добавляются только несколько строк без смены стадии и без смены смысла документа, правка вносится в текущий файл без повышения версии.

В корне `docs2/` лежит только одна актуальная версия каждого основного документа.
Предыдущие версии хранятся в `docs2/history/` по семействам файлов.

## 3. Правило по стилю работы

По умолчанию ответы даются в режиме критика:
- без лести;
- без автосогласия;
- с прямым исправлением ошибок;
- с фиксацией рисков, слабых мест и альтернатив;
- при нехватке данных - с прямым указанием, чего именно не хватает.

Стиль - жестко, коротко, по существу.

## 4. Что остается обязательным

- сначала читаются rules и migration context;
- потом восстанавливается стадия проекта и риски;
- только после этого предлагаются roadmap или патчи;
- все outputs и логи - только через корневую `out/`;
- кодовые патчи - архивом и только с измененными файлами.
