# model_plan_v1.2 - сводный план развития модели и системы

Файл: `docs2/model_plan_v1.2.md`

Эта версия дополняет `model_plan_v1.1.md`:
- этап 1.1 переводится в режим агента;
- фокус полностью очищается от roadmap вокруг `legacy`;
- план фиксируется как серия коротких итераций с проверяемыми результатами.

## 0. Актуальная рамка планирования

Текущая общая рамка:
- финальная цель - исследовательски честная offline/online система;
- песочница - промежуточный этап к online;
- `core` - главный и единственный рабочий контур развития;
- `legacy` - архивный reference, без отдельного roadmap и без обязательных parity-сравнений;
- Dataset A truth policy фиксируется как:
  - `Dataset A_research = candidates`
  - `Dataset A_policy = trades`.

## 1. Что меняется в подходе к этапу 1.1

Этап 1.1 больше не ведется как большой архитектурный рефакторинг одним блоком.
Он ведется в режиме агента:
- шаги по 1-2 действия;
- каждый шаг привязан к конкретным файлам;
- после каждого шага обязателен self-check;
- при нехватке файла или сомнении в версии правки стоп.

Цель этапа 1.1 не меняется:
- новая архитектура `core`-бэктестера;
- тонкий `backtest.py` как фасад;
- явное разделение signal path / snapshots / entry gating / execution / reporting / runner;
- без скрытого изменения стратегии под видом рефакторинга.

## 2. Этап 1.1 в режиме агента

### 1.1.A - Зафиксировать контракты фасада

Действия:
1. ввести `app2/range/core/contracts.py`;
2. облегчить `app2/range/core/backtest.py`, не меняя CLI-контракт.

Результат:
- появляются явные dataclass-контракты;
- `backtest.py` перестает быть местом анонимных tuple и ad hoc state.

Self-check:
- синтаксическая проверка измененных файлов;
- smoke import `app2.range.core.backtest`.

Stop-condition:
- если в текущем архиве отсутствует актуальный `app2/range/core/backtest.py`, шаг не выполняется.

### 1.1.B - Вынести data/config I/O

Действия:
1. создать `app2/range/core/data_io.py`;
2. перенести из фасада загрузку config и OHLCV.

Результат:
- фасад не знает деталей чтения файлов;
- путь данных и чтение свечей централизуются.

Self-check:
- синтаксическая проверка;
- smoke-run функции загрузки на одном символе, если входные данные есть в архиве.

Stop-condition:
- если структура входных данных не видна или не приложена, шаг ограничивается только безопасным выносом без изменения поведения.

### 1.1.C - Вынести snapshot analytics

Действия:
1. создать `app2/range/core/snapshots.py`;
2. перенести расчет entry snapshot analytics из `backtest.py`.

Результат:
- geometry / ATR / slope / distance analytics живут отдельно от execution loop;
- downstream для Dataset A получает более стабильный snapshot layer.

Self-check:
- синтаксическая проверка;
- проверка, что старые snapshot columns не исчезли.

Stop-condition:
- если текущий snapshot contract неочевиден по фактическому `app2`, сначала фиксируется карта колонок, патч не расширяется дальше.

### 1.1.D - Вынести entry gating

Действия:
1. создать `app2/range/core/entry_gating.py`;
2. перенести feature prep, threshold logic и optional model gating.

Результат:
- ML gating больше не размазан по orchestration-слою;
- появляется чистая точка для будущего inference layer.

Self-check:
- синтаксическая проверка;
- smoke import без включения модели;
- если gating включаемый, режим `off` должен работать как раньше.

Stop-condition:
- если текущий код зависит от внешней модели, отсутствующей в архиве или окружении, шаг ограничивается структурным выносом без обещаний по полному smoke-run модели.

### 1.1.E - Вынести execution loop

Действия:
1. создать `app2/range/core/execution.py`;
2. перенести trade loop и связку с `risk.py`.

Результат:
- execution становится отдельным policy-layer;
- `backtest.py` больше не открывает и не закрывает сделки сам.

Self-check:
- синтаксическая проверка;
- короткий synthetic smoke-test на базовом `sig_df`, если это возможно без внешних данных.

Stop-condition:
- если synthetic контур не удается собрать безопасно, шаг завершается только компиляцией и структурной проверкой.

### 1.1.F - Вынести reporting

Действия:
1. создать `app2/range/core/reporting.py`;
2. вынести сериализацию trades / stats / snapshots / debug.

Результат:
- артефакты `out/` пишутся через отдельный слой;
- контракт файлов для Dataset A становится явнее.

Self-check:
- синтаксическая проверка;
- проверка путей записи только в корневой `out/`.

Stop-condition:
- если текущий naming contract неочевиден, сначала фиксируется фактическая схема имен из `app2`, без тихого переименования.

### 1.1.G - Вынести runner

Действия:
1. создать `app2/range/core/runner.py`;
2. перенести symbol-task orchestration и aggregate run.

Результат:
- `backtest.py` становится реальным thin facade;
- symbol-run и multi-symbol run отделяются от остальной логики.

Self-check:
- синтаксическая проверка;
- smoke import runner и backtest.

Stop-condition:
- если параллельный контур (`parallel_map` или эквивалент) зависит от неактуального файла, шаг не расширяется до переписывания параллелизма.

### 1.1.H - Финальная зачистка фасада

Действия:
1. удалить остатки дублированной логики из `app2/range/core/backtest.py`;
2. при необходимости поправить `app2/cli.py`, только если комментарии или routing противоречат фактическому `core`.

Результат:
- `backtest.py` остается точкой входа, а не повторным монолитом;
- CLI не лжет о состоянии `core`.

Self-check:
- compileall для измененных python-файлов;
- при наличии локальных данных - минимальный smoke-run `python -m app2.cli range-v3-backtest ...`.

Stop-condition:
- если входных данных для честного smoke-run нет, нельзя придумывать несуществующую проверку; в ответе прямо фиксируется, чего не хватило.

## 3. Критерии приемки этапа 1.1

Этап закрывается только если одновременно выполнено следующее:
- `backtest.py` стал thin facade;
- signal path, snapshots, entry gating, execution, reporting и runner разделены по модулям;
- CLI-контракт сохраняется;
- артефакты продолжают писаться только в `out/`;
- downstream для Dataset A не ломается по naming и базовым колонкам;
- self-check выполнен на каждом шаге.

## 4. Что не входит в этап 1.1

В 1.1 не входят:
- roadmap и сравнения с `legacy`;
- новый Dataset A manifest;
- новый `inference.py`;
- online execution;
- redesign risk policy;
- расширение model zoo;
- общая перестройка всего `cli.py` за пределами необходимых корректировок.

## 5. Главные риски этапа 1.1

- скрытая смена торгового поведения под видом рефакторинга;
- поломка snapshot contract для Dataset A;
- повторное залипание ML-gating в orchestration-слое;
- попытка расширить этап 1.1 до dataset/inference before stabilization;
- нехватка актуальных файлов или входных данных для честного smoke-run.
