# CONTRACTv1.0 - архитектурный и data-контракт проекта

Файл: `docs2/CONTRACTv1.0.md`

Это единый рабочий контракт `docs2`, собранный из версий `CONTRACTv1.0`-`CONTRACTv1.2`.
Мелкие редакционные правки без изменения source of truth не требуют новой версии имени файла.

## 0. Актуальная рамка контракта

- `core` - единственный рабочий контур развития;
- `legacy` - только архивный reference, без отдельного roadmap и без обязательных сравнений;
- offline/sandbox/online рассматриваются как одна траектория, где sandbox - промежуточный этап;
- `docs2` - обязательный слой фиксации договорённостей;
- Dataset A truth policy фиксируется как:
  - `Dataset A_research = candidates`
  - `Dataset A_policy = trades`.

## 1. Как читать этот контракт

- сначала читаются `PROJECT_RULES_v1.0.md` и `MIGRATION_CONTEXT_v1.0.md`;
- затем этот контракт сопоставляется с фактическим состоянием `app2`;

## 1. Контуры системы

### 1.1. Legacy lane
Назначение:
- reference;
- sanity-check;
- контроль регрессий;
- архивный baseline.

Ограничения:
- не является основным направлением развития;
- допускаются только bugfix, совместимость и диагностические правки;
- не должен быть местом для новых архитектурных решений.

### 1.2. Core lane
Назначение:
- главный контур развития;
- основная боевая архитектура;
- база для перехода к sandbox и online.

Инварианты:
- должен быть модульным;
- не должен превращаться в новый монолит;
- не должен прятать business logic в glue-коде.

### 1.3. Dataset / ML lane
Назначение:
- исследовательский и боевой слой для Dataset A/B, baseline ML, CatBoost и будущих моделей.

Инварианты:
- развивается только вместе с data policy;
- не может игнорировать leakage discipline;
- не должен смешивать research truth и policy analysis без явной маркировки.

## 2. Архитектурные инварианты

Перенос из CONTRACTv4.8-v4.10 и уточнение под docs2:

1. `backtest` оркестрирует, но не становится центром логики всей системы.
2. `state_machine` отвечает только за сигналы и debug-info.
3. `risk` отвечает только за исполнение, ограничения и состояние риска.
4. `metrics`, `portfolio`, `stats` отвечают только за расчёт метрик.
5. `geometry` отвечает за аналитическое описание диапазона и не управляет execution напрямую.
6. `dataset` не должен использовать future-only labels как features.
7. source-of-truth для risk config должен быть единым.
8. offline и online boundary должны быть зафиксированы явно.
9. leakage validator обязателен, но не считается формальным доказательством.
10. ChatGPT, Qwen и agent_hands не могут обходить контракт.

## 3. Два режима Dataset A

### 3.1. Dataset A_research
- source: `candidates`
- назначение: поиск edge и обучение входной модели
- это главная исследовательская правда для входного ML

### 3.2. Dataset A_policy
- source: `trades`
- назначение: анализ поведения текущего rule/core policy
- это не заменяет `A_research`, а дополняет его

### 3.3. Общие требования
Для любого Dataset A должны логироваться:
- `entry_mode`
- interval
- symbol universe
- config id / risk profile
- активные фильтры
- тип label

## 4. Dataset B и offline labels

### 4.1. Dataset B
- используется для in-trade анализа и моделей выхода;
- строится по барам открытой сделки;
- должен содержать meta, trade-level, bar-level и feature-колонки в согласованном формате.

### 4.2. Offline-only labels
- `y_exit` может использовать информацию следующего бара;
- такой label считается offline-only;
- он не может использоваться в rolling/live path без новой версии контракта;
- leakage validator и ручное ревью обязательны.

## 5. Risk core

### 5.1. Общие инварианты
- риск рассчитывается через `risk.py` или эквивалентный выделенный слой;
- side-effects risk слоя ограничены:
  - обновлением risk-state;
  - вычислением qty / SL / TP;
  - решением открыть / закрыть позицию;
- риск-ядро не должно делать feature engineering.

### 5.2. Входы risk core
- `equity`
- `risk_pct_per_trade`
- `sl_pct`
- `tp_pct`
- `daily_dd_limit_pct`
- `max_consecutive_losses`
- активный `risk_profile`

### 5.3. Выходы risk core
- `RiskState`
- флаги ограничения торговли
- флаги вроде `post_circuit_breaker` в сделках

### 5.4. Пессимистичный execution contract
Смысл, ранее обсуждённый и закреплённый в старых документах, сохраняется как направление:
- вход по `open` следующего бара после сигнала;
- при конфликте SL и TP на одном баре берём консервативный вариант;
- gap и weekend policy обрабатываются жёстко.

### 5.5. Weekend no-hold
- `--no-hold-weekend` является hard risk-rule;
- при включении позиции перед выходными закрываются;
- новые позиции на барах, уходящих в weekend-gap, блокируются;
- soft-фильтры и AI не могут переопределять это правило.

### 5.6. Risk profiles
- `prod_baseline` - боевой профиль;
- `diag_fullrun` - диагностический профиль.
- необходимо прийти к одному source-of-truth для risk config;
- дублирование одинакового смысла между `params` и `risk_profiles` считается риском архитектурного дрейфа и подлежит устранению.

## 6. Data and leakage policy

### 6.1. Rolling path
Запрещено:
- `shift(-k)` в decision path;
- обращение к future OHLC при принятии решения на баре t;
- подмешивание offline-only labels в live features.

### 6.2. Offline path
Разрешено:
- использовать будущее для labelers и offline analysis;
- использовать offline-only labels для research и обучения;
- но только при явной маркировке и изоляции от rolling/live logic.

### 6.3. Leakage validator
- leakage validator обязателен;
- является guardrail, а не формальным доказательством;
- должен использоваться вместе с ручным ревью data path.

## 1. Два движка Range: legacy и core

### 1.1. Legacy Range V3

**Назначение:** базовый, честный, но убыточный эталон.

- Реализован в `range_v3_legacy.py` + `v3_backtest_legacy.py`.
- Использует:
  - rolling-окна для построения диапазонов,
  - риск-ядро с фиксированными параметрами,
  - robust ATR-фильтр,
  - диагностический slope-фильтр (не влияет на входы/выходы).
- PF<1 допускается: цель legacy — **сохранить поведение**, а не заработать.

**Инварианты legacy:**
- Формат входного DataFrame (по тикеру):
  - индекс — datetime (UTC или локальный, но монотонный),
  - колонки: минимум `open`, `high`, `low`, `close`, `volume`,
  - при наличии доп. колонок (ATR, regime, фичи) они не меняют логику Range.
- Формат `trades.csv` и `stats.json` стабилен в рамках v4.9.
- Любой патч в legacy-ядро ограничивается:
  - bugfix’ами,
  - техдолгом (оптимизация, логгинг),
  - но не меняет смысла сигналов, входов/выходов и risk core.

### 1.2. Range core_v4 (offline)

**Назначение:** новое модульное офлайн-ядро Range, которое будет развиваться дальше и станет основой для online-модели.

- Реализуется в `app2/range/core/` (поддиректории `geometry.py`, `state_machine.py`, `risk.py`, `features.py` и т.п.).
- Работает строго в офлайн-режиме поверх исторических данных (bar-level).
- Может расходиться по PF/WinRate с legacy, но:
  - на этапе «чистого переноса» (первый скелет core) PF/WinRate должны быть в пределах разумной дельты от legacy (≈ ±0.1 PF, ±2–3 п.п. WinRate);
  - все дальнейшие улучшения фиксируются в changelog’е и увязываются с изменениями параметров/фильтров.

## 2. Data-контракт Range core_v4

### 2.1. Входные данные (per symbol, per TF)

Для фабрики core_v4:

- на вход подаётся DataFrame по одному тикеру и одному таймфрейму;
- индекс — datetime, строго монотонный;
- обязательные колонки:
  - `open`, `high`, `low`, `close`, `volume`;
- допустимы дополнительные фичи, но они не должны требовать look-ahead в rolling-режиме.

Для offline-labeler’ов (geometry, AAA/AA/A) допускается использование будущих данных,
но их результаты могут использоваться **только как таргеты/фичи** и не должны напрямую попадать
в расчёт сигналов на момент t (см. политику leakage).

### 2.2. Выходы

Любой модуль core_v4 должен явно описывать:

- `signals_df`:
  - индекс = dt,
  - минимум колонки: `v3_signal` / `entry_signal` / `exit_signal` (по контракту конкретного модуля);
- `debug_info`:
  - словарь с диагностикой, включающий:
    - структуру диапазонов (L/U/H/M),
    - доли валидных боксов,
    - маски фильтров (height/slope/vol),
    - метрики risk core (кол-во стопов, превышения дневных лимитов и т.п.).

Формат конкретных полей фиксируется в под-контрактах модулей (`geometry`, `state_machine`, `risk`).

## 3. Risk core — общие инварианты

Независимо от того, legacy это или core_v4, risk core обязан соблюдать:

1. **Размер позиции:**
   - рассчитывается через `risk_pct_per_trade` и волатильность/ATR;
   - не может превышать лимиты по инструменту и портфелю (параметры конфига).

2. **SL/TP:**
   - уровень SL и TP выражен в процентах от входной цены (`sl_pct`, `tp_pct`);
   - SL всегда ближе к цене входа, чем TP (по крайней мере при типовых настройках);
   - если на одном баре цена касается и SL, и TP — считается, что сработал SL (пессимистичный сценарий).

3. **Модель исполнения:**
   - вход по **open следующего бара** после сигнала;
   - выход по SL/TP на баре, где они были достигнуты модельно (по high/low и направлению сделки);
   - при gap’ах через уровень стопа/тейка используется консервативная схема (хуже из разумных вариантов).

4. **Анти-«усиление риска»:**
   - запрещено расширять SL или увеличивать риск-процент по мере удержания сделки;
   - разрешено только ужесточать стоп (trailing, перевод в безубыток и т.п.).

5. **Ограничения по дню / серии:**
   - `max_consecutive_losses` — после N подряд убыточных сделок стратегия обязана перестать открывать новые позиции до конца дня / окна;
   - `daily_dd_limit_pct` — при превышении дневной просадки от equity0 или от начала дня стратегия отключается до следующего дня.

Подробные формулы закрепляются в модуле `risk.py` для core_v4 и описываются в приложении к этому контракту.

## 4. Политика data leakage и Leakage Validator v1

### 4.1. Общие правила

1. В **rolling-логике core_v4** запрещено:
   - использовать `shift(-k)` (k>0) для любых фич или сигналов;
   - обращаться к значениям `close_{t+1}`, `high_{t+1}`, `low_{t+1}` при принятии решения на баре t;
   - подмешивать offline-результаты, которые сами используют look-ahead, в rolling-фичи без явной задержки.

2. **Offline-алгоритмы** (labelers, таргеты, AAA/AA/A и т.п.) могут использовать будущее,
   но их выходы должны быть помечены как такие, и при подключении в rolling-часть обязаны иметь:
   - либо задержку ≥ 1 бар,
   - либо явное исключение из набора фич для live-решений.

### 4.2. Leakage Validator v1

Вводится вспомогательный инструмент `leakage_validator.py` (app2 или app3), который:

- анализирует пайплайн генерации фич/сигналов на предмет:
  - использования `shift(-k)`,
  - suspicious колонок с явными «future»-паттернами в именах,
  - некорректных join/merge по времени;
- может запускаться как CLI-команда (например, `python -m app2.cli leakage-check ...`).

**Важно:** Validator v1 — это **диагностический инструмент, а не формальное доказательство** отсутствия leakage.  
Решение о готовности пайплайна к production принимается комбинацией:
- результатов валидатора,
- код-ревью,
- и backtest/forward-test анализов.

## 5. LLM-инструменты: ChatGPT, Qwen, агентский режим

### 5.1. ChatGPT (ручной режим)

- Работает по следующим правилам:
  - не меняет CONTRАCT и README напрямую — только через новые версии файлов в `docs/`;
  - все изменения кода отдаёт в виде патч-архивов с изменёнными файлами, с явным дифф-ТЗ;
  - не создаёт своих `data/` / `out/` внутри `app2/` или `app3`.

- Обязан уважать:
  - структуру директорий проекта,
  - режим «только изменённые файлы»,
  - запрет на «тихие» архитектурные упрощения без обсуждения.

### 5.2. Qwen (локальный помощник)

- Может:
  - помогать искать баги,
  - экспериментировать с параметрами,
  - предлагать правки кода.
- Не может:
  - в одностороннем порядке менять архитектуру,
  - считаться источником истины без фиксации в документации.

Любое изменение, пришедшее от Qwen, считается допустимым только после того, как:
- обсуждено здесь,
- оформлено в виде ТЗ,
- реализовано патчем,
- и отражено в `docs/`.

### 5.3. Агентский режим ChatGPT

Агентский режим (автоматический запуск последовательностей задач) рассматривается как **инструмент для будущих фаз**.

**Допустимые задачи для агента:**
- запуск бэктестов по заранее заданному списку сценариев;
- сбор и агрегация метрик, генерация отчётов;
- рефакторинг кода в рамках уже существующей архитектуры (без изменения контракта).

**Запрещено для агента:**
- модифицировать risk core или его параметры без явного ТЗ и ревью;
- менять структуру данных и форматы `trades/stats`;
- создавать/удалять файлы вне `app2/`, `app3/`, `data/`, `processed/`, `out/`, `docs/`;
- изменять CONTRACT или README.

**Условия включения агентского режима:**
- core_v4 показывает PF ≥ 1 на устойчивом интервале offline-тестов;
- пайплайн прошёл базовую проверку Leakage Validator v1;
- проведено ручное ревью ключевых модулей (geometry, state machine, risk).

После каждого использования агентского режима обязателен короткий отчёт (в `docs/` или отдельном лог-файле),
чтобы можно было отследить, какие изменения были сделаны.

## 0. Область действия (дополнение)

CONTRACTv4.10 дополняет зону `app2/range/core/` и вводит обязательные блоки:

- `engine.py` — точка входа core_v4 (подготовка параметров, вызовы state machine).
- `state_machine.py` — генерация сигналов и debug_info (каузальная логика, без циклов по барам).
- `geometry.py` — геометрия диапазонов (L/U/H/M, geo_class, geo_valid_box), **только аналитика**.
- `risk.py` — риск-ядро core_v4: расчёт размера позиции, SL/TP, дневные лимиты, consecutive losses.
- `metrics.py` — метрики на уровне одной сделки/тикера (PnL, per-symbol stats).
- `portfolio.py` — агрегаты портфеля (PF/WinRate/MaxDD/TotalReturn) по списку сделок.
- `stats.py` — общие утилиты для статистик (например, `pnls_to_stats`).
- `backtest.py` — оркестрация: загрузка данных, запуск core, вызовы risk/metrics/portfolio, формирование артефактов.

---

## 1. Принцип модульности core_v4

### 1.1. Разделение ответственности

1. **State Machine** (`state_machine.py`) отвечает только за сигналы и debug_info.
2. **Risk** (`risk.py`) отвечает только за исполнение (entry/exit), ограничения и состояние риска.
3. **Metrics / Portfolio / Stats** отвечают только за вычисление метрик.
4. **Backtest** (`backtest.py`) не содержит бизнес-логики риска и метрик — только оркестрация.

### 1.2. Запреты (modularity constraints)

- Запрещено смешивать вычисления метрик и risk-логики внутри state machine.
- Запрещено дублировать функции статистик в нескольких местах (общие функции — в `stats.py`).
- Любые изменения в risk-логике должны происходить только в `risk.py`.

## 2. Risk core — уточнение контрактных блоков

Risk core обязан быть реализован через `risk.py` и не должен иметь side-effects вне:
- обновления risk-state,
- вычисления SL/TP/qty,
- принятия решения об открытии/закрытии.

Входы:
- `equity`, `risk_pct_per_trade`, `sl_pct`, `tp_pct`,
- дневные лимиты `daily_dd_limit_pct`,
- лимит `max_consecutive_losses`.

Выходы:
- `RiskState` (equity, max_dd, daily_dd, disabled flags),
- `post_circuit_breaker` флаг в сделках.

### 2.1. Weekend no-hold (core)
- Hard-правило риска, включаемое флагом `--no-hold-weekend` (core backtest).
- При включении: закрываем открытые позиции перед выходными и не открываем новые позиции на барах, которые уходят в weekend-gap.
- Правило не зависит от AI и не может быть переопределено soft-фильтрами.

### 2.2. Risk profiles (RangeV3)
- Конфиг: `app2/range/config.json` → `RangeV3.risk_profile` + `RangeV3.risk_profiles`.
- `prod_baseline`: боевой профиль с текущими лимитами риска.
- `diag_fullrun`: диагностический профиль с сильно ослабленными лимитами (для full-run анализа).

## 3. Метрики и портфельные агрегаты

- `metrics.py` — метрики на уровне тикера:
  - `compute_trade_pnl`, `compute_pnl_rel`, `build_symbol_metrics`.
- `portfolio.py` — агрегированные метрики портфеля:
  - `build_portfolio_stats`.
- `stats.py` — общий расчёт базовой статистики по массиву PnL:
  - `pnls_to_stats`.

Метрики не влияют на торговые решения и используются только для отчётности.

## 4. Dataset A/B (Phase 1) — data contract

Источник данных:
- артефакты `range-v3-backtest` (legacy/core) по каждому тикеру:
  - `*_trades.csv`,
  - `*_snapshots.csv`.

CLI-генератор:
```bash
python -m app2.cli range-v3-make-datasets \
  --symbols SBER GAZP LKOH GMKN ROSN \
  --interval 30min \
  --out-prefix out/range_v3/ALL_30m_BASE \
  --tag v3seg_base \
  --mode entry|intrade|both \
  --exit-improve-threshold 0.0000 \
  --exit-min-bars 0
```

### Dataset A — Entry Snapshots
- 1 строка на сделку.
- Join: `entry_dt` ←→ `snapshots.datetime`.
- Минимальный набор:
  - `symbol`, `entry_dt`, `exit_dt`, `direction`,
  - feature-колонки (все, кроме служебных: `datetime`, `symbol`, `open/high/low/close/volume` и т.п.),
  - label-метрики: `pnl_rel`, `pnl_abs`, `bars_in_trade`, `max_adverse_excursion` (если доступны).

### Dataset B — In-Trade Time-Series
- 1 строка на бар во время открытой сделки (`entry_dt`..`exit_dt` включительно).
- Цена для расчёта PnL:
  - по `close` (если есть), иначе по `open`.
- Минимальный набор колонок:
  - meta: `symbol`, `interval`, `trade_id`, `trade_uid`, `dt`,
  - trade-level: `entry_dt`, `exit_dt`, `direction`, `entry_price`, `exit_price`, `qty`,
    `trade_pnl_abs`, `trade_pnl_rel`, `trade_bars_in_trade`, `trade_exit_reason`,
  - bar-level: `bars_held`, `time_since_entry_min`, `pnl_abs`, `pnl_rel`,
    `mae_abs`, `mfe_abs`, `mae_rel`, `mfe_rel`, `y_exit`,
  - features из snapshots (по умолчанию все колонки кроме `datetime/symbol`).
- Допустимые дополнительные колонки:
  - `entry_*`, `exit_*`, `post_*`, `geo_*` (контекст входа из core/legacy).

### Label `y_exit` (v1, offline-only)
`y_exit = 1`, если:
- `pnl_rel_{t+1} >= trade_pnl_rel + exit_improve_threshold`, и
- `bars_held >= exit_min_bars`.

Иначе `y_exit = 0`. Последний бар сделки всегда `0`.

**Важно:** `y_exit` использует информацию следующего бара, поэтому это
**offline-лейбл**. Он не должен попадать в rolling-логику сигналов и не может
использоваться в live-режиме без новой версии контракта.
