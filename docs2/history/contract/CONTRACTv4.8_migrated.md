# CONTRACTv4.8 — Архитектурный и data-контракт MOEX APP2+

Файл: `docs/CONTRACTv4.8.md`  
Связан с:
- `docs/READMEv4.8.md` — миграционный README и статус проекта,
- `docs/model_plan_v0.3.md` — детальный план развития модели,
- будущими версиями CONTRACTv4.9+ (по мере эволюции архитектуры).

Этот документ фиксирует **то, что считается «нормой»** для текущей версии проекта:
- какие входы / выходы гарантирует код;
- как устроена цепочка *Regime → Strategy → Risk*;
- какие инварианты НЕЛЬЗЯ нарушать при дальнейших патчах (вручную, через ChatGPT или через агентский режим).

## 0. Область действия

**Текущее покрытие CONTRACTv4.8:**

- `app2`:
  - модуль `range/`:
    - `range_v3.py` (rolling Range V3),
    - `v3_backtest.py` (бектестер для Range V3),
    - `app2/range/config.json` (локальный конфиг Range V3),
  - `app2/cli.py` (команда `range-v3-backtest` как внешний интерфейс).
- Директории данных:
  - `data/` — сырые бары (MOEX/Tinkoff),
  - `processed/` — агрегированные бары (10m/30m/1h…),
  - `out/` — все результаты/логи (строго в корне репо, **не** в `app2/`).

**Пока НЕ покрыто напрямую (только уровнем планов):**

- `app3` (MTL-ядро, онлайн-обучение),
- дополнительные стратегии (Trend, MeanRev v2, Dynamic Regime Strategy),
- продвинутый MLOps.

## 1. Интерфейс Range V3 (уровень CLI)

Единственный «официальный» внешний интерфейс Range V3:

```bash
python -m app2.cli range-v3-backtest \
  --symbols SBER GAZP LKOH GMKN ROSN \
  --interval 30min \
  --equity0 1000000 \
  --config-range app2/range/config.json \
  --out-prefix out/range_v3/ALL_30min_FILTERS_v0_xx \
  --tag filters_v0_xx
```

**Гарантии:**

1. Команда не читает/не пишет ничего вне:
   - `data/`, `processed/`, `out/`, `app2/range/`.
2. Все артефакты бектеста пишутся в `out/` с префиксом `--out-prefix`:
   - `*_trades.csv`,
   - `*_per_symbol_stats.csv`,
   - `*_stats.json`,
   - `*_debug.json`.
3. Формат файлов `trades` и `stats` стабилен в рамках v4.8 и описан ниже.

## 2. Data-контракт Range V3

### 2.1. Входы Range V3 (run_range_v3_for_symbol)

Функция `run_range_v3_for_symbol(df, params)` ожидает:

- `df: pd.DataFrame` с индексом по времени (`DatetimeIndex`), содержащий минимум:
  - `open`, `high`, `low`, `close`, `volume`,
  - дополнительные служебные колонки (если есть): `regime_*`, индикаторы и т.д.
- `params: RangeV3Params`, который читает настройки из `app2/range/config.json` (секция `RangeV3.params`).

**Обязательные поля `RangeV3.params` (по состоянию v4.8):**

- Геометрия диапазона:
  - `range_window_bars` — окно для rolling-квантилей,
  - `min_range_height_pct`, `max_range_height_pct` — допустимая высота бокса относительно цены,
  - `entry_zone_alpha`, `shadow_pct` — зона входа у нижней границы.
- Сигнальная логика:
  - флаги/параметры для включения/отключения отдельных фильтров, если они есть.
- Риск-ядро:
  - `risk_pct_per_trade`,
  - `max_bars_in_trade`,
  - `max_consecutive_losses`,
  - `daily_dd_limit_pct`,
  - `sl_pct`, `tp_pct`.
- Волатильность и фильтры режима:
  - `atr_window`,
  - `atr_pct_min`, `atr_pct_max`,
  - `atr_min_valid_frac`, `atr_min_valid_bars`,
  - `slope_k`.

### 2.2. Выходы Range V3 (run_range_v3_for_symbol)

Функция возвращает:

```python
sig_df: pd.DataFrame
debug_info: Dict[str, Any]
```

**Гарантии по колонкам `sig_df`:**

- Индекс — `DatetimeIndex` (те же бары, что на входе, возможно с небольшим укорочением головы).
- Минимальный набор колонок:
  - `close` — цена закрытия (проколлектирована из исходного `df`),
  - `v3_L`, `v3_U`, `v3_M`, `v3_H` — границы и высота диапазона (NaN там, где бокса нет),
  - `v3_signal` — конечный buy/sell сигнал Range V3:
    - `0` — нет входа,
    - `+1` — long-сигнал (для текущей реализации),
    - `-1` — short-сигнал (зарезервировано на будущее),
  - любые дополнительные диагностические колонки (по мере добавления).

**Гарантии по `debug_info`:**

- Содержит ключ `rolling_diag` с полями:
  - `roll_L_notna_frac`,
  - `valid_box_frac`,
  - `mask_height_frac`,
  - `mask_slope_frac`,
  - `mask_vol_frac`,
  - `atr_notna_frac`,
  - `signals_count`.
- Диагностика используется для настройки параметров, но **не должна ломать контракт формата**:
  - новые поля разрешены,
  - удалять существующие поля без обновления CONTRACT — запрещено.

## 3. Контракт риск-ядра (Range V3 Risk Core)

Риск-ядро реализовано в `app2/range/v3_backtest.py` внутри функции
`_run_trades_from_signals(symbol, sig_df, params, equity0)`.

### 3.1. Открытие позиции

- Открытие позиции возможно **только** на барах, где `v3_signal != 0`.
- Для каждой новой позиции:

  ```python
  risk_capital = equity * params.risk_pct_per_trade
  sl_dist = price * params.sl_pct
  qty = risk_capital / sl_dist
  ```

  Инварианты:

  - `qty > 0` — иначе вход не происходит.
  - `sl_dist > 0` — иначе вход не происходит.
  - Итого: при срабатывании стопа убыток по сделке ≈ `equity * risk_pct_per_trade` (с поправкой на дискретизацию цены и проскальзывание).

- Уровни SL/TP:

  - Long:
    - `sl_price = entry_price * (1 - sl_pct)`
    - `tp_price = entry_price * (1 + tp_pct)`
  - Short (зарезервировано):
    - `sl_price = entry_price * (1 + sl_pct)`
    - `tp_price = entry_price * (1 - tp_pct)`

### 3.2. Закрытие позиции

Позиция закрывается при первом по времени событии:

1. **Срабатывание SL или TP** на текущем баре:
   - проверяется по `high/low` бара,
   - при срабатывании используется соответствующий уровень `sl_price`/`tp_price` как цена выхода.
2. **Смена сигнала** (`v3_signal == -position_side`) — смена режима/направления.
3. **Превышение `max_bars_in_trade`** — защита от вечных сделок.
4. (Опционально в будущем) Срабатывание AI-блоков выхода (после Фазы 3).

После закрытия:

- пересчитывается `equity`,
- обновляется `max_drawdown`,
- счётчик `consec_losses`:
  - увеличивается, если `pnl < 0`,
  - обнуляется, если `pnl >= 0`.
- Если `consec_losses >= max_consecutive_losses` — бэктест по инструменту досрочно прекращается (каскадное поражение).

### 3.3. Жёсткие инварианты риск-ядра

1. **Никакая логика (в т.ч. AI в будущем) не имеет права:**
   - отменять или отодвигать сработавший SL;
   - увеличивать `risk_pct_per_trade` сверх значения из конфига без явного обновления CONTRACT.
2. PnL по сделке всегда считается как:

   ```python
   pnl = (exit_price - entry_price) * qty * side
   ```

3. Запрещено:

   - открывать позицию без сигнала `v3_signal`,
   - торговать инструмент вне списка `--symbols` CLI,
   - писать что-либо в `out/` вне префикса `--out-prefix`.

## 4. Инварианты по данным и каузальности

1. Все фильтры режима в rolling-режиме (**включая ATR и slope**) используют только информацию из прошлого:
   - `shift(1)` для цен и производных индикаторов;
   - `rolling(..., min_periods=...)` без заглядывания в будущее.
2. Offline-labeler (если используется) может использовать «будущее», но:
   - его артефакты не должны подмешиваться в rolling-бектест;
   - смешение offline/online логики без обновления CONTRACT запрещено.
3. Все новые фичи/индикаторы обязаны:
   - либо быть строго каузальными;
   - либо быть явно помеченными как offline-артефакты (и не попадать в реалтайм-пайплайн без пересмотра CONTRACT).

## 5. Организация работы и использования LLM-инструментов

### 5.1. Общий рабочий цикл

1. Формулируется **дифф-ТЗ** (в чате).
2. На его основе готовится **патч**:
   - только изменённые файлы,
   - в zip-архиве.
3. Перед отправкой патча:
   - синтаксическая проверка (минимум `ast.parse` / `py_compile`),
   - по возможности маленький dry-run на синтетике.
4. Все результаты бектеста/диагностики:
   - только в корневой `out/`,
   - без дополнительных `out/` внутри `app2/` или `app3/`.
5. Никакие фундаментальные упрощения/смены архитектуры не вносятся «молча»:
   - только через обсуждение и обновление CONTRACT/README/плана.

### 5.2. Использование ChatGPT (текущий режим)

- ChatGPT работает в режиме «ручного ассистента»:
  - помогает формулировать дифф-ТЗ,
  - собирает патчи (код и конфиги),
  - анализирует логи/результаты бектеста.
- Ограничения:
  - не читать/не изменять файлы вне пересланных архивов/фрагментов,
  - не вставлять полный код файлов в чат (если это явно не запрошено),
  - не запускать тяжелые свипы параметров до того, как стратегия выйдет в плюс на дефолтных параметрах (отражено и в плане).

### 5.3. Использование Qwen (локальный LLM) как инструмента багфикса

- Qwen используется как **вспомогательный инструмент**:

  - локально прогоняет те же команды,
  - анализирует трейсбеки и логи,
  - предлагает точечные правки.

- Контракт по Qwen:

  1. Все архитектурно значимые решения (смена структуры данных, риск-логики, добавление новых режимов) **обязательно проходят через CONTRACT + README + model_plan**.
  2. Qwen не меняет контракт — он только помогает быстрее найти технические ошибки.
  3. Любое изменение, сделанное по подсказке Qwen, всё равно должно быть:
     - описано в дифф-ТЗ,
     - оформлено патчем и проверено.

## 6. ТЗ для агентского режима (черновая фиксация)

**Агентский режим** — будущий режим, в котором LLM получает доступ к ограниченному «инструментальному» окружению (вроде CI), где может:

- запускать команды (`python -m app2.cli ...`),
- читать артефакты из `out/`,
- вносить мелкие патчи в код,
- вести лог своих действий.

### 6.1. Задачи, разрешённые для агентского режима

1. **Диагностические прогоны и отчёты:**
   - запуск отдельных backtest-команд (Range V3, позже Trend/MeanRev),
   - сбор и агрегация метрик по `*_stats.json` и `*_trades.csv`,
   - генерация кратких отчётов по сериям экспериментов.

2. **Технические патчи низкого риска:**
   - рефакторинг без изменения логики (разбиение файлов, вынос утилит),
   - добавление логирования/диагностики,
   - правка явных багов, подтверждённых тестами (off-by-one, неверный ключ в dict, опечатки).

3. **Свипы и перебор параметров** — ТОЛЬКО после того, как:
   - базовая стратегия по фазе (например, Range V3) демонстрирует устойчивый плюс на дефолтных параметрах,
   - критерии фиксации этого «плюса» задокументированы в model_plan и CONTRACT.

### 6.2. Жёсткие ограничения агентского режима

1. Агент не имеет права:

   - менять ключевые риск-параметры (`risk_pct_per_trade`, `daily_dd_limit_pct`, SL/TP) без обновления CONTRACT/README/плана;
   - добавлять новые входы/выходы функций, ломая контракт;
   - писать в директории вне `out/`, `app2/`, `app3/` и `docs/`.

2. Любая архитектурная правка (новые режимы, heads, датасеты, контракты модели) **делается только в ручном режиме** через:

   - обсуждение,
   - обновление `docs/model_plan_v*.md`,
   - обновление `docs/CONTRACTv*.md`,
   - затем — патч.

3. Каждая сессия агентского режима должна:

   - иметь ограничение по количеству шагов (итераций),
   - завершаться отчётом:
     - какие команды были запущены,
     - какие файлы изменены,
     - какие метрики улучшились/ухудшились.

### 6.3. Этапы включения агентского режима (по плану)

1. **Этап A (после Фазы 0 и 1):**  
   Агент используется только для:

   - повторного прогона уже известных сценариев,
   - свёрстанных заранее наборов экспериментов,
   - генерации отчётов.

2. **Этап B (после появления AI-ядра в app3):**  
   Ограниченное авто-тюнинг окружения (hyperparam sweep, retrain-скрипты) с:

   - жёсткими ограничениями по риску,
   - логированием всех изменений.

3. **Этап C (опционально, в далёком будущем):**  
   Частичная автономия внутри песочницы брокера (paper trading) с:

   - невозможностью перейти к реальным деньгам без явного ручного подтверждения и отдельного CONTRACTvX.Y.

## 7. Как обновлять CONTRACT

1. Любое изменение, которое:
   - добавляет/убирает поля в `RangeV3.params`,
   - меняет формат `sig_df`, `debug_info` или `*_stats.json`,
   - меняет инварианты риск-ядра,
   требует:
   - новой версии CONTRACT (v4.9, v5.0, …),
   - ссылки на соответствующую версию model_plan.

2. Старые версии CONTRACT и README **не удаляются**, а служат историей для миграций между чатами и окружениями.




## Regime Layer Contract (Diagnostic v0)

- Controls ONLY entry permission
- MUST NOT:
  - force exit
  - modify risk
  - generate signals

- v0 is diagnostic, self-confirming
- NOT production regime engine
