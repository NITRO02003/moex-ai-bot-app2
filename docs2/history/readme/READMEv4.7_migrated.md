# READMEv4.7 — MOEX APP2+ / Range V3 (миграция чата)

## 0. Контекст версии

Эта версия README фиксирует состояние проекта на момент:

- реализован и включён в код **Range V3** для `app2`:
  - многосегментная логика (AAA/AA сегменты),
  - новая реализация `range_v3.py`,
  - новый backtester `v3_backtest.py` с агрегацией по тикерам.
- Команда:

  ```bash
  python -m app2.cli range-v3-backtest \
    --symbols SBER GAZP LKOH GMKN ROSN \
    --interval 30min \
    --equity0 1000000 \
    --config-range app2/range/config.json \
    --out-prefix out/range_v3/ALL_30min_v3 \
    --tag v3seg
запускается без ошибок, но по всем тикерам количество сделок = 0.

Это наш зафиксированный базовый чекпоинт перед переездом в новый чат.

1. Производственные правила (напоминание)
Патчи только в архиве и только изменённые файлы.
При изменении кода отправляем zip только с изменёнными файлами, не весь проект.

Если есть сомнения в версии файла — правки стоп.
Если файл не виден / отсутствует / есть сомнения в актуальности:

правки не вносим;

явно запрашиваем актуальную версию или новый архив.

Все выводы и логи — только через корневую out/.
Все результаты (equity, отчёты, свипы, диагностика, forward-тесты и т.п.) — в корне проекта out/.
Внутри app2/ и app3/ своих out/, data/ и т.п. не создаём.

Self-check перед отправкой патча.

минимально: ast.parse / python -m compileall,

по возможности: короткий dry-run на синтетике или малом наборе тикеров.

Не вставлять полный код файлов в чат (если ассистент сам не попросил).
Полный код — только по явному запросу.

Любые спорные архитектурные упрощения — только после обсуждения.
Никаких скрытых «упростил под капотом» без фиксации в ТЗ/README.

3. Текущий статус Range V3 (на момент v4.7)
3.1. Что реализовано в range_v3.py
RangeV3Params — доступ к параметрам через свойства (ATR-квантили, размеры рейнджа, deadzones, риск и т.п.).

RangeSegmentV3(start_idx, end_idx, quality):

сегмент классифицируется по качеству "AAA" / "AA" / "A" по количеству тестов границ.

detect_range_segments_v3:

находит кандидаты в рейндж-сегменты по:

квантилям ATR (atr_low_q–atr_high_q),

малому наклону MA (почти горизонтальный рынок),

минимальной длине сегмента (range_window_bars).

build_range_box_v3:

считает L/U/H/M/shadow для сегмента,

фильтрует по относительной высоте рейнджа (min_range_height_pct–max_range_height_pct).

generate_signals_v3_for_segment:

для каждого AAA/AA сегмента:

строит нижнюю и верхнюю «зоны входа»,

вводит deadzone по ATR и по времени (утро/вечер/пятница),

отмечает breakout через v3_breakout,

генерирует сигналы v3:

первая отметка уровня — только «touch»,

повторный заход в зону — вход (long/short).

apply_breakout_logic_v3:

если подряд несколько v3_breakout баров ≥ breakout_bars, сигналы в этой фазе обнуляются.

run_range_v3_for_symbol:

находит все сегменты, отфильтровывает AAA/AA,

строит box для каждого сегмента,

«сшивает» сигналы всех сегментов в один датафрейм,

если ни одного подходящего сегмента нет — стратегия не торгует по символу (везде v3_signal = 0).

3.2. Что реализовано в v3_backtest.py
_load_ohlcv:

ищет processed/{symbol}_{interval}.csv, иначе data/{symbol}.csv,

пытается угадать колонку с датой/временем,

нормализует open/high/low/close/volume.

run_range_v3_for_symbol:

вызывается для каждого символа, возвращает:

датафрейм с сигналами и debug-полями,

debug-структуру по сегментам.

_run_trades_from_signals:

простая логика сделок поверх v3_signal:

фиксированная доля риска risk_pct_per_trade,

обычный SL-дистанционный суррогат (1% от цены),

ограничение по барам в сделке (max_bars_in_trade),

лимит по числу подряд убыточных сделок (max_consecutive_losses).

main(args):

для каждого символа:

грузит данные, считает сигналы, считает сделки,

сохраняет:

{prefix}_{symbol}_{interval}_{tag}_stats.json,

{...}_trades.csv,

{...}_snapshots.csv,

{...}_debug.json.

по всем символам:

собирает все трейды в единый ALL_*_trades.csv,

считает портфельные PF, winrate, maxDD,

сохраняет:

*_ALL_{interval}_{tag}_stats.json,

*_ALL_{interval}_{tag}_per_symbol_stats.csv.

4.1. Этап 1 — Диагностика Range V3 (сегменты и пороги)
Анализ по тикерам:

открыть *_per_symbol_stats.csv:

увидеть по каждому тикеру: trades, total_pnl, pf, win_rate, max_drawdown.

сейчас trades=0 — задача убедиться, что:

действительно нет AAA/AA сегментов,

или сегменты есть, но сигналов внутри нет.

Анализ *_debug.json по тикерам:

смотреть:

segments_total,

segments_tradable,

segments_used (список с start/end/L/U/H/M/quality).

ключевые вопросы:

есть ли вообще сегменты по текущим параметрам?

сколько AAA/AA сегментов на тикер / интервал?

не слишком ли узкие или широкие рейнджи (height_pct)?

Подбор порогов сегментации:

параметры для ручного/DS-подбора:

atr_low_q, atr_high_q — дефолт: 0.2–0.8,

min_range_height_pct, max_range_height_pct — дефолт: 0.002–0.02,

min_tests_AAA, min_tests_AA — дефолт: 3 / 2,

порог по наклону MA (0.0005 * close).

цель:

добиться появления разумного числа AAA/AA сегментов,

не превращая всё в «режим range всегда».

Результат этапа: параметры, при которых Range V3 хотя бы локально торгует и даёт ненулевой PF по отдельным тикерам.

4.2. Этап 2 — Выходы и подтверждения для Range V3
Когда базовая сегментация настроена:

Разработка выходов:

сценарии:

TP в противоположной зоне рейнджа (от L → U и наоборот),

TP1/TP2 с частичным фиксированием,

SL за уровнем (L − k·ATR, U + k·ATR),

тайм-аут: если цена застряла около M слишком долго, закрывать.

Подтверждения входа:

свечной price action (реакция от уровня: хвост, разворотная свеча и т.п.),

простой momentum-фильтр (не входить, если микротренд слишком сильный),

объёмный фильтр (избегать «тонких» мест),

при возможности — фильтр времени внутри дня (оставить только «живые» часы).

Результат этапа: Range V3 с понятной логикой входа/выхода и ненулевым количеством сделок; цель — выйти к PF > 1 и winrate > 50% хотя бы на части тикеров.

4.3. Этап 3 — Data Science по фичам (для Range / AI)
Отдельный крупный блок (после стабилизации базового Range V3):

Сбор базы кейсов по рейнджам:

выгружать сегменты и сделки в out/ в виде CSV:

параметры рейнджа (L/U/H/M, длительность, ATR, ADX),

характеристики входа/выхода,

исход сделки (win/lose, pnl, rr).

Свип и отбор фич:

тестировать фичи:

ATR/ADX, различные price-отношения, candle-статы, volume-статы,

синтетические комбинации (бивариантные/мультвариантные фичи).

отбрасывать фичи, которые:

не улучшают стабильность PF,

не добавляют объяснимости.

Готовим базу для AI:

итоговая фича-база должна:

быть достаточно информативной,

содержать минимальный мусор,

позволить обучать AI-модели без чрезмерной подгонки порогов.

4.4. Этап 4 — Интеграция Range V3 в общую архитектуру

чёткое разделение:

trend → trend-стратегии,

Связка с rule-backtest / regime-backtest:

детектирования режима,

генерации сигналов,
