## 0. Производственные правила (TL;DR)

Эти правила остаются в силе и критичны:

1. **Патчи только в архиве и только изменённые файлы.**
   - Не шлём весь проект, только zip с изменёнными файлами.
   - В чате описываем:
     - какие файлы изменены,
     - что именно поменяли,
     - команды для self-check / запуска.

2. **Если есть сомнения в версии файла — правки стоп.**
   - Если файл не виден / есть сомнения, что он актуальный:
     - правки не делаем,
     - сначала явно просим актуальную версию файла или новый архив.

3. **Все выводы и логи — только через корневую `out/`.**
   - В корне репо:
     - `data/` — сырые данные,
     - `processed/` — агрегированные бары,
     - `out/` — все результаты, отчёты, свипы, forward-тесты и т.д.
   - Внутри `app2/` и `app3/` **не создаём свои `out/`, `data/` и т.п.**

4. **Self-check перед отправкой патча.**
   Обязательный минимум:
   - `python -m compileall app2` (или нужный подмодуль),
   - по возможности маленький dry-run (обычно SBER, один интервал).
   Не отправляем заведомо некомпилирующийся код.

5. **Не вставлять полный код файлов в чат (если явно не попросили).**
   - В обычном режиме:
     - описываем изменения словами,
     - прикладываем zip-патч,
     - не копипастим целые файлы.
   - Полный файл — только если ассистент прямо просит «вставь сюда файл целиком».

6. **Любые спорные архитектурные упрощения — только через обсуждение.**
   - Если хочется «схитрить» и упростить архитектуру:
     - сначала формулируем идею и обсуждаем,
     - только потом меняем фундаментальную логику.

7. **Структура директорий:**
   - В корне:
     - `data/`, `processed/`, `out/`.
   - Внутри `app2/`/`app3/`:
     - только логика, никаких собственных `data/`/`out/`.

8. **Стандарт вызова CLI:**
   - Все команды:
     - `python -m app2.cli <command> [аргументы]`
   - Примеры в README и коде обязаны быть реально запускаемыми.

9. **Режимы — основа логики.**
   - Сначала определяем **режим рынка** (`trend / range / high_vol` и уточнения),
   - потом выбираем стратегию и параметры.
   - Любые новые фичи/стратегии должны вписываться в режимную декомпозицию, а не обходить её.

10. **Свип — инструмент диагностики, а не «подгонка под красоту».**
    - Свип параметров/фич используется для:
      - диагностики,
      - оценки устойчивости,
      - построения профилей (`conservative / balanced / aggressive`).
    - Не используем свип как «магический оптимизатор», который всё подгоняет на истории.

## 1. Состояние проекта на v4.6

### 1.1. Архитектура

- **`app/`** — первая версия бота (исторический артефакт).
- **`app2/`** — основная боевая версия:
  - режимная архитектура (`trend`, `range`, `high_vol`),
  - CLI через `python -m app2.cli ...`.
- **`app3/`** — перспективная архитектура под более модульную/ML-ориентированную реализацию (в работе).

Отдельно выделена директория:

- **`app2/range/`** — логика для `range`-режима:
  - `config.json` (конфиг range V2 — хранит параметры режима и сценариев),
  - `backtest.py` (range-backtest engine),
  - `batch.py` / `summary.py` (батчи и агрегаты),
  - `feature_sweep.py` (новый модуль для свипа фич).

### 1.2. Trend-режим

- Сделаны эксперименты через `rule-backtest` по трендовой стратегии.
- На дефолтных параметрах тренд **не показал стабильной положительной доходности**.
- На момент v4.6:
  - **trend поставлен на паузу**,
  - фокус перенесён на `range`, так как он статистически доминирует по времени нахождения рынка в этом режиме и потенциально даёт больший «импакт».

Нет ни одной устойчиво прибыльной зоны (PF ≥ 1 при достаточном числе сделок) в текущем виде стратегии, если не считать статистически слабые хвосты.

Свип чётко выделил состояния, где:

PF заметно выше базового, но < 1.

Эти состояния логично использовать как основу для:

4.2.2. Профиль range_v2_conservative
Идея:

Максимально ужесточить фильтры,

Оставить только «самые чистые» mean-reversion ситуации,

Сильно урезать количество сделок,

Попробовать вытащить PF хотя бы к 1+.

Фильтры по фичам (квантильные диапазоны):

dist_from_ma:

использовать нижний диапазон квантилей, где отклонение вниз от MA максимально:

цель: примерно q ∈ [0.0, 0.1] (нижние 10% по модулю).

edge_proximity (или напрямую band_pos):

вход только близко к границе диапазона (нижние квантильные уровни):

цель: q ∈ [0.0, 0.2] по edge_proximity (близко к нижней полосе).

bar_body_pct:

исключить «мусорные» мелкие бары:

q ≥ 0.7 (верхние 30% по доле тела).

range_vs_atr:

брать только бары, которые существенно больше средней волатильности:

q ≥ 0.7.

Фильтры по времени:

Часы:

разрешить только наиболее адекватные по свипу:

ориентир: hour ∈ {9, 10, 11, 17, 18, 20}
(точный список уточняется по *_time_hour.csv, минимум — исключить 12–14, 19 и «очень тонкие» часы).

Дни недели:

фокус на наиболее устойчивых днях:

day_of_week ∈ {1, 2} → вторник и среда (в нумерации 0=Mon).

4.2.3. Профиль range_v2_balanced
Идея:

Чуть ослабить фильтры относительно conservative,

Увеличить количество сделок,

Сохранить улучшенный PF относительно базы.

Фильтры по фичам:

dist_from_ma:

расширить диапазон mean-reversion:

ориентир: q ∈ [0.0, 0.3].

edge_proximity:

разрешить более широкий пояс у границы:

q ∈ [0.0, 0.4] по edge_proximity.

bar_body_pct:

убрать только совсем слабые бары:

q ≥ 0.5.

range_vs_atr:

чуть мягче:

q ≥ 0.5.

Фильтры по времени:

Часы:

разрешить «ядро» сессии:

ориентир: hour ∈ {9, 10, 11, 16, 17, 18, 20}
(т.е. выкидываем провальные часы 12–14, 19; остальное — по результатам).

Дни недели:

добавить четверг:

day_of_week ∈ {1, 2, 3} → Tue, Wed, Thu.

4.2.4. Профиль range_v2_aggressive
Идея:

Самый широкий профиль,

Максимум сделок,

Стремиться хотя бы к заметно лучшему PF относительно «голого» range V2 без фильтров.

Фильтры по фичам:

dist_from_ma:

позволить более широкий диапазон mean-reversion:

q ∈ [0.0, 0.5].

edge_proximity:

разрешить почти весь диапазон, но с отсечением совсем «центра»:

q ∈ [0.0, 0.6].

bar_body_pct:

минимальное требование к телу бара:

q ≥ 0.3 (или даже чуть ниже, по результатам).

range_vs_atr:

лёгкий фильтр:

q ≥ 0.3.

Фильтры по времени:

Часы:

выкинуть только явно провальные зоны:

исключить 12–14 и 19,

остальное оставить.

Дни недели:

разрешить все дни:

day_of_week ∈ {0, 1, 2, 3, 4} (Mon–Fri),

возможно, при необходимости исключить конкретный день, если свип покажет глубокий слив.

Важно:

4.3.2. Общее описание изменения кода (будущий патч)

range-backtest:

Добавить CLI-параметр:

--profile range_v2_conservative | range_v2_balanced | range_v2_aggressive | None.

При запуске:

если --profile задан:

загрузить app2/range/config.json,

взять соответствующую секцию profiles[profile_name],

построить объект фильтров (по фичам и времени),

применять фильтры при принятии решения о входе в сделку.

если --profile не задан:

поведение по умолчанию = текущая логика (стратегия как есть, без дополнительных профильных фильтров).

range-batch / range-summary:

Научить их понимать профили:

прогон по всем тикерам для каждого профиля,

сводные отчёты «по профилям».

Не трогаем:

саму логику расчёта PnL, risk-модуль, структуру бэктеста — только фильтрацию входов.
