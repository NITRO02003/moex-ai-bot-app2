## 1. Базовые принципы (рамочные договорённости)

1. **Вертикальный срез перед масштабом.**  
   Любая стратегия сначала проверяется на срезе:

   > 1 тикер × 1 таймфрейм × 1 явно заданный рыночный режим

   Пока на этом срезе стратегия не даёт базовый edge (PF, win_rate, адекватная просадка) —  
   _запрещены_ свипы, мульти-тикерные прогоны и усложнения.

2. **Иерархия решений: режим → стратегия → параметры.**

   ```text
   Режим рынка → Разрешённые стратегии → Параметры
   ```

   Не наоборот. Стратегии не должны работать «везде и всегда».

3. **Единый риск-слой.**  
   Все стратегии живут поверх общей риск-платформы:

   - sizing по волатильности / ATR,
   - дневные и общие лимиты просадки,
   - global circuit breakers.

   Стратегия не тянет с собой собственный «зоопарк» риск-логики.

4. **Запрет свипов для убыточных стратегий.**  
   Пока на вертикальном срезе PF < 1.1 — нельзя:

   - добавлять фичи «на удачу»,
   - запускать свипы,
   - переносить стратегию в портфель.

   Разрешены только изменения архитектуры сигналов и режимных фильтров.

5. **Инфраструктурные упрощения не могут ломать логику.**  
   Любое упрощение «ради удобства»:

   - если оно противоречит концепции стратегии или режимной логике,
   - всегда выносится на обсуждение, а не принимается молча.

6. **MeanRev — нишевая стратегия, а не ядро.**  
   MeanRev включается только там, где он _по определению_ должен работать:

   - боковики и low_vol режимы,
   - ограниченный набор тикеров.

   Основной драйвер доходности системы — Trend / Breakout.

7. **Рабочие правила взаимодействия с ChatGPT.**

   - Патчи всегда присылаются **в архиве и только с изменёнными файлами**.
   - Если версия файла под вопросом — правки стоп, сначала запрос актуального файла.
   - Все пути вывода/логов по умолчанию — в корневую папку `out/`.
   - Перед отправкой патча ассистент делает self-check (хотя бы `ast.parse` / минимальный dry-run).
   - Ответы после правок кода — максимально краткие: «что поменял» + ссылка на архив (без дампа кода).
   - Любые спорные решения по архитектуре/упрощению — выносить на обсуждение.

## 2. Целевая архитектура системы

### 2.1. Уровень рынка

Вводим явную режимную декомпозицию:

- `trend_bull`, `trend_bear`
- `range_high_vol`, `range_low_vol`
- `volatility_spike`, `transition`

Режимы определяются комбинацией:

- динамики цены (MA / наклон / ADX),
- волатильности (ATR / realized vol),
- при необходимости — календарных факторов.

### 2.2. Роли стратегий

- **Trend**  
  - Работает в `trend_bull` / `trend_bear`.  
  - Задача: зарабатывать на устойчивых направленных движениях.  
  - Основной источник PnL.

- **Breakout**  
  - Работает в `transition` / `volatility_spike`.  
  - Задача: ловить импульсы, пробои диапазонов / экстремумов.

- **MeanRev (V2.1 и далее)**  
  - Работает только в `range_high_vol` / `range_low_vol`.  
  - Задача: зарабатывать на локальных перегревах вокруг справедливого уровня.  
  - Нишевой модуль, дополняющий Trend/Breakout.

- **AI / ML**  
  - Не отдельная стратегия, а надстройка:
    - фильтр сигналов,
    - режимный детектор,
    - калибратор параметров.
  - Не должен использоваться как «магическая кнопка edge» при сломанной архитектуре.

### 2.3. Риск-слой

Общий для всех стратегий:

- расчёт рекомендуемого размера позиции из заданной `target_vol` / `risk_per_trade`,
- дневные и недельные лимиты просадки,
- ограничение общей экспозиции по портфелю и по одному инструменту,
- глобальные стоп-кнопки при аномальной динамике PnL.

### Фаза 1. Proof of Concept для Trend (один вертикальный срез)

**Цель:** показать, что мы можем сделать _одну_ стратегию устойчиво прибыльной в _правильном_ режиме.

1. **Выбор среза:**

   - Стратегия: `Trend`
   - Тикер: SBER (или другой ликвидный флагман)
   - Таймфрейм: базовый рабочий (например, 30min)
   - Период: явно трендовый участок 2022 года

2. **Формальная спецификация Trend-стратегии:**

   - Условия входа/выхода (MA, пробои, фильтры по волатильности / объёму).
   - Разрешённые режимы рынка.
   - Ограничения по частоте сделок и максимальной экспозиции.

3. **Метрики и инварианты для PoC:**

   Минимальные требования на выбранном срезе (примерные ориентиры):

   - PF ≥ 1.1
   - Win rate ≥ 52%
   - Max drawdown ≤ 10–15%
   - Разумное количество сделок (нет гиперскальпинга)

4. **Процесс:**

   - Разобрать текущую реализацию Trend в коде и привести её в соответствие с ТЗ.
   - Прогнать только на выбранном срезе.
   - При необходимости — изменить архитектуру сигналов и фильтров (но не впадать в «overfit»).

**Выход Фазы 1:**  
Одна стратегия (Trend) демонстрирует базовый edge в своём режиме на одном тикере.

### Фаза 2. Портфельное ядро: Trend + Breakout + риск-слой

**Цель:** собрать устойчивое ядро системы без MeanRev.

1. **Расширение Trend:**

   - добавление 2–3 ключевых тикеров,
   - проверка, что архитектура переносится без катастрофического падения метрик.

2. **Подключение Breakout:**

   - формальная спецификация Breakout (в каких режимах живёт, какие сигналы),
   - PoC на одном тикере в `transition` / `volatility_spike`,
   - инварианты по риску и частоте сделок.

3. **Общий риск-слой:**

   - унификация sizing,
   - единые дневные и недельные лимиты,
   - общие правила остановки торговли при аномальных просадках.

4. **Портфельный бэктест Trend+Breakout:**

   - агрегированный PnL по портфелю,
   - max_dd, PF, sharpe, зависимость от режимов рынка.

**Выход Фазы 2:**  
Ядро системы (Trend+Breakout+общий риск-слой) демонстрирует приемлемую доходность и контролируемый риск на нескольких ключевых тикерах.

### Фаза 3. MeanRev V2.1 как нишевой модуль

**Цель:** вернуть MeanRev, но уже в правильной роли и архитектуре.

1. **Формальный концепт MeanRev V2.1:**

   - Режимы: только `range_high_vol` / `range_low_vol`.
   - Нормализация сигнала:
     - входы по классическому z-score `(price - rolling_mean) / rolling_std`,
     - ATR используется отдельно для стопов/тейков и sizing’а.
   - Асимметрия long/short:
     - более агрессивные лонги (меньший |z|),
     - более консервативные шорты (больший |z|),
     - опциональный режим «long-only» для устойчивых ап-трендов.
   - Ограничения по активности:
     - max входов в день по тикеру,
     - cooldown между входами,
     - min-hold по барам.

2. **PoC MeanRev V2.1:**

   - 1–2 тикера, где по истории есть длительные боковики.
   - Отдельный тест по range-режимам (без трендовых участков).
   - Критерии допуска к свипам:
     - PF ≥ 1.1 в своих режимах,
     - win_rate ≥ 58–60%,
     - адекватный объём сделок.

3. **Интеграция в портфель:**

   - проверка, как MeanRev влияет на общую просадку и PF системы,
   - контроль корреляции PnL с Trend/Breakout.

**Выход Фазы 3:**  
MeanRev либо занимает своё нишевое место в портфеле, либо откладывается, если edge не подтверждается.

### Фаза 4. AI / ML и адаптивность

**Цель:** добавить AI сверху на уже рабочую архитектуру.

1. **Режимный детектор на AI:**

   - ML-модели для классификации режимов рынка,
   - калибровка на исторических фазах.

2. **Фильтры сигналов:**

   - модели, отбрасывающие заведомо слабые сигналы стратегий,
   - оценка эффекта на PF / win_rate.

3. **Адаптивные параметры:**

   - постепенный переход от ручных сеток к адаптивным параметрам,
   - но только после того, как базовая архитектура и роли стратегий стабильны.

## 4. Как использовать этот план в работе

- Любая новая идея / фича / изменение сначала проверяется на соответствие этому документу:
  - нарушает ли она архитектуру или принципы риска,
  - к какой фазе относится,
  - какие инварианты должна сохранять.
- Перед переходом к следующей фазе:
  - фиксируем, что критерии текущей фазы достигнуты,
  - сохраняем результаты (логи, отчёты, конфиги) как «контрольную точку».

Этот документ — «карта местности», а не код. По мере прогресса версии (v4.2, v4.3, …) будут фиксировать эволюцию архитектуры и критериев.
